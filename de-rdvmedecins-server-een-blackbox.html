    8. De RdvMedecins-server, een blackbox

    De voorbeelden 22 tot en met 25, gevolgd door de casus, communiceren met een server: de JSON-server van de applicatie [RdvMedecins]. Dit is de [NestJS]-server van de cursussen [React], [Vue.js], [Angular] en [Flutter]: de server van de cursus [NestJS], waarvan de controllers geen HTML-pagina's meer genereren maar JSON-antwoorden produceren. Lezers van die cursussen kennen dit hoofdstuk al; het wordt hier vrijwel ongewijzigd overgenomen en zij kunnen zich uitsluitend richten op de paragraaf over authenticatie, waarin wordt uitgelegd wat er verandert voor een mobiele applicatie.

    In deze cursus is deze server een blackbox: u hoeft niet te weten hoe hij is geschreven. Het enige wat telt is de API, dat wil zeggen de lijst met HTTP-verzoeken die hij accepteert en de antwoorden die hij retourneert. Dit is de gebruikelijke situatie voor een clientontwikkelaar: de API is een contract en het serverteam kan achter dat contract alles wijzigen wat het wil. De broncode wordt meegeleverd (map [rdvmedecins-nestjs-json]) en is uitgebreid van commentaar voorzien, voor de nieuwsgierige lezer.

    In dit hoofdstuk wordt uitgelegd hoe u de server installeert, wordt de API beschreven en wordt de server bevraagd met [curl].

    8.1. De applicatie RdvMedecins

    De applicatie beheert afspraken voor een huisartsenpraktijk. Er zijn drie rollen:

    Rol
    Wie
    Wat mag deze rol doen
    [ADMIN]
    De beheerder ([admin])
    Afspraken inplannen en annuleren voor alle patiënten; artsen en cliënten beheren
    [DOCTOR]
    Artsen ([pelissier], [tatou], [dupont])
    Afspraken inplannen en annuleren voor alle patiënten; alle namen in de agenda's zien
    [USER]
    Patiënten ([martin], [durand], [bistrou], [german])
    Afspraken voor zichzelf maken; hun afspraken annuleren; hun account beheren. In een agenda zien zij de namen van andere patiënten niet

    Demo-accounts gebruiken hun login als wachtwoord. De beheerregels worden door de server gecontroleerd, ongeacht de client:

    • geen afspraken in het verleden;
    • slechts één toekomstige afspraak per patiënt;
    • een tijdvak kan per dag maar één keer worden geboekt;
    • twee artsen (of twee cliënten) mogen niet dezelfde voor- en achternaam hebben; een login hoort bij slechts één account;
    • een arts met geplande afspraken kan niet worden verwijderd;
    • een record dat intussen door iemand anders is gewijzigd, kan niet worden overschreven (optimistische vergrendeling);
    • een patiënt krijgt nooit de naam van een andere patiënt toegewezen.

    8.3. Antwoordformaat

    Alle URL's beginnen met [/api]. Een geslaagd verzoek krijgt een statuscode 2xx en, in de body, de gevraagde gegevens in JSON-formaat. Een afgewezen verzoek krijgt een statuscode 4xx of 5xx en, in de body, een fout die ALTIJD hetzelfde formaat heeft:

    1
2
3
4
5
6
    {
  "statusCode": 400,
  "key": "ERRORS.INVALID_FORM",
  "params": { "min": "6" },
  "fields": { "lastName": "ERRORS.LASTNAME_REQUIRED", "password": "ERRORS.PASSWORD_TOO_SHORT" }
}
    • [statusCode]: de HTTP-code, herhaald in de body;
    • [key]: de vertaalsleutel van het bericht. De server retourneert nooit tekst die moet worden weergegeven: hij kent de taal van de gebruiker niet meer. De client vertaalt de sleutel met zijn woordenboeken (zie voorbeeld 21);
    • [params] (optioneel): de parameters van het bericht ([At least {min} characters], [Try again in {minutes} minute(s)]);
    • [fields] (optioneel): bij een afgewezen formulier de fout voor elk veld.

    8.4. Authenticatie

    De client authenticeert zich met [POST /api/auth/login], met een gebruikersnaam, een wachtwoord en een antwoord op de CAPTCHA. In ruil daarvoor stuurt de server in de header [Set-Cookie] van zijn antwoord een cookie met een ondertekend JWT-token:

    1
    Set-Cookie: rdvmedecins_jwt=eyJhbGciOiJIUzI1NiIs...; Max-Age=7200; Path=/api; HttpOnly; SameSite=Strict

    De client moet dit cookie vervolgens bij elk verzoek aan [/api] meesturen, in de header [Cookie]: zo weet de server wie het verzoek doet.

    Deze server is ontworpen voor webclients en zijn ontwerpkeuzen worden bepaald door de risico's die specifiek zijn voor webbrowsers:

    • [HttpOnly]: de [JavaScript]-code op de pagina kan dit cookie niet lezen. Een kwaadaardig script dat in de pagina is ingevoegd, kan het token dus niet stelen. Gevolg voor de client: hij kan niet zelf bepalen of hij is ingelogd. Hij vraagt het aan de server ([GET /api/auth/me]);
    • [Path=/api]: het cookie wordt alleen meegestuurd bij verzoeken aan de API;
    • [SameSite=Strict]: de browser voegt het cookie alleen toe aan verzoeken die vanaf een pagina van deze site worden verstuurd. Een kwaadaardige pagina op een andere site kan de browser niet laten handelen namens de gebruiker (een zogeheten CSRF-aanval);
    • [Max-Age=7200]: het verloopt na twee uur, op hetzelfde moment als het token.

    Een tweede beveiliging tegen CSRF-aanvallen: de server weigert (415) elk POST-verzoek waarvan de body niet in JSON is. Een gecompromitteerd HTML-formulier op een andere site kan geen JSON versturen.

    En een mobiele app? Daar is geen browser: niemand bewaart het cookie of stuurt het uit zichzelf terug. De app neemt die rol over: de bibliotheek [OkHttp], die een „cookie jar" (een [CookieJar]) toevertrouwd krijgt, leest de header [Set-Cookie] uit de antwoorden en schrijft de header [Cookie] in de verzoeken (voorbeeld 23). De attributen [HttpOnly] en [SameSite] gelden alleen voor browsers: ze hebben hier geen effect, net zoals ze geen effect hebben op [curl].

    8.6. De API bevragen met curl

    De servermap [curl] bevat de JSON-bodies van de verzoeken in dit hoofdstuk, met één bestand per verzoek. Bijvoorbeeld [curl/login-admin.json]:

    1
    { "login": "admin", "password": "admin", "captchaId": "-", "captcha": "test" }

    De opdrachten worden ingevoerd in een console die is geopend in de directory [rdvmedecins-nestjs-json]. Enkele opties van [curl]:

    • [-i]: toon ook de antwoordheaders; [-s]: zonder voortgangsbalk;
    • [--json @file]: verstuur de inhoud van het bestand met POST, met de header [Content-Type: application/json] (curl 7.82 en hoger; bij een oudere versie gebruikt u [-H "Content-Type: application/json" -d @file]);
    • [-X PUT], [-X DELETE]: de HTTP-methode;
    • [-c cookies.txt]: sla de ontvangen cookies op in dit bestand; [-b cookies.txt]: stuur ze terug. Zo „blijft" [curl] van de ene opdracht op de andere ingelogd, net als een browser.

    Onder [PowerShell] moet u [curl.exe] invoeren en niet [curl] (dat daar naar een andere opdracht verwijst). De wat uitgebreide JSON-antwoorden zijn voor dit document opgemaakt en de headers [Date], [ETag], [Connection], en [Keep-Alive] zijn verwijderd.
